# 配置缓存损坏时类型错误阻断自动重建

## 观察到的行为

静态审查发现类型约束阻断原有缓存恢复分支，审查优先级为 P2；现已按授权运行复现并完成修复。

- V3 将 `SlimApp::$configs` 声明为 `array`。
- `src/SlimApp.php:90` 将 `unserialize()` 的结果直接赋给该属性。
- 缓存被判定 fresh 但内容损坏时，返回的 `false` 引发 `TypeError`，程序无法进入后续重建分支。

## 期望行为

反序列化失败或结果不是配置数组时，应用将缓存视为无效，重新解析原始配置并重建缓存。

## 复现步骤

以下步骤仅操作测试专用缓存，不修改真实应用配置或缓存。

1. 在隔离的临时应用目录加载有效配置，生成配置缓存及其元数据。
2. 保留资源文件及缓存元数据，将配置缓存内容改为不能反序列化的内容。
3. 重建应用实例并再次加载配置，确保缓存 freshness 检查仍通过。
4. 断言应用恢复原始配置并重建有效缓存，记录实际异常与堆栈。

## 影响

使用 SlimApp 配置缓存的应用可能在缓存损坏后启动失败，直至人工删除缓存。
正常缓存不受影响；本项不涉及旧业务数据格式兼容或数据迁移。

## 所需回归证据

回归必须同时证明缓存损坏、freshness 条件成立以及恢复行为。

- 修复前：上述条件下出现给 `array` 属性赋值的 `TypeError`。
- 修复后：损坏缓存和非数组结果均触发重建，合法缓存仍可正常读取。
- 版本依据：当前运行代码与 `v3.2.1` 一致；V2 的无类型属性可接收 `false` 并进入重建分支。
