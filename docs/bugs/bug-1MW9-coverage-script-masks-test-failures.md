# 覆盖率脚本吞掉测试失败并可能返回成功

## 观察到的行为

静态审查发现覆盖率脚本丢失测试退出状态，审查优先级为 P2；尚未运行复现测试。

- `tests/run_all_coverage.sh:24` 在 PHPUnit 管道后使用 `|| true`。
- 第 31 和 37 行对子进程同样使用 `|| true`，并丢弃标准错误输出。
- 后续合并成功时，测试失败不会作为脚本的失败状态返回。

## 期望行为

任何非预期测试失败均使总脚本返回非零状态，并保留定位失败所需的证据。
`parallel_fail` 的预期失败应单独验证，不能据此忽略所有子进程错误。

## 复现步骤

以下步骤仅在隔离测试工程中注入失败，不修改正常业务用例。

1. 为脚本准备可合并的覆盖率数据，并让其中一个 PHPUnit 用例确定性断言失败。
2. 运行覆盖率脚本，断言其保留失败信息并以非零状态退出。
3. 在另一个场景中使本应成功的 fork 脚本异常退出，验证总脚本同样失败。
4. 增加全部成功和业务预期失败的对照场景，避免测试只验证脚本总是失败。

## 影响

人工或 CI 可能把失败测试当作成功，覆盖率报告也可能掩盖未通过的测试。
本项影响验证结果的可信度，不直接影响生产业务运行；脚本当前属于辅助覆盖率入口。

## 所需回归证据

回归必须分别验证 PHPUnit、fork 进程和成功对照的退出状态。

- 修复前：至少一个确定失败场景在合并成功后仍返回零状态。
- 修复后：非预期失败返回非零，失败原因可追溯，全部成功时返回零。
- `parallel_fail` 必须按预期业务结果判定，不能把任意退出码 255 都视为通过。

## 执行约束

用户指定分阶段 TDD，由人工确认红灯并启动修复。

1. 后续仅编写能复现本 Bug 的测试，不修改生产代码，不自动运行测试。
2. 由人工运行测试，确认失败源于本 Bug，并保存命令、日志及测试报告。
3. 等待人工明确启动 Bug 修复流程后，再修改实现并运行回归验证。
