# Fix

在当前 checkout 修复单个已有 Bug：澄清、确认有效红灯、修复并验证、标为
`fixed`。不切分支、不 start、不走交付主线、不 code-review、不 close-out。

## 决策树

```text
┌──────────────────────────────────┐
│ 1 Check                          │
└────────────────┬─────────────────┘
                 │
                 ├──── 失败/缺失 ─────────────→ [停止并报告]
                 ├──── fixed 且回归仍通过 ────→ [只读核对后结束]
                 │
                 ▼ open，或 fixed 但验证失败
┌──────────────────────────────────┐
│ 2 Clarify                        │
└────────────────┬─────────────────┘
                 │
                 ├──── 失败/缺失 ────→ [不修复，停止]
                 │
                 ▼ 通过
┌──────────────────────────────────┐
│ 3 Reproduce                      │
└────────────────┬─────────────────┘
                 │
                 ├──── 失败/缺失 ────→ [停止并报告]
                 │
                 ▼ 有效红灯已记录
┌──────────────────────────────────┐
│ 4 Repair                         │
└────────────────┬─────────────────┘
                 │
                 ├──── 未满三轮且下一步明确 ────→ 4 Repair
                 ├──── 目标不明或无法完成 ──────→ [停止并报告]
                 │
                 ▼ 修复完成且验证已通过
┌──────────────────────────────────┐
│ 5 Record                         │
└────────────────┬─────────────────┘
                 │
                 ├──── 通过 ─────────→ [结束]
                 └──── 失败/缺失 ────→ [停止并报告]
```

## 工作流（唯一执行契约）

读取 `references/common.md` 与 `references/object-contract.md`。
步骤 2 读取并内部执行 `references/clarify.md`。
CLI 使用 `python3 "$MDF_ROOT/scripts/mdf.py"`。
独立调用只推进当前 intent；不由 deliver 内部委托。

| # | 步骤 | 类型 | 做什么 | 证据 | 通过 → | 失败/缺失 → |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | Check | 脚本 | 核对入口、分支、Bug 与回归 | doctor、list | open 或未过则 2；fixed 仍过则只读结束 | 停止并报告 |
| 2 | Clarify | 约束 | 内部 clarify 修复范围与方案 | 共同理解 | 3 | 不修复，停止 |
| 3 | Reproduce | 约束 | 确认或编写该 Bug 的有效红灯测试 | 命令、退出状态、失败断言 | 4 | 停止并报告 |
| 4 | Repair | 约束 | 红灯转绿并 smart（quick suite） | 命令、退出状态、smart | 5 | 未满三轮且下一步明确则 4；否则停 |
| 5 | Record | 脚本 | 标为 `fixed`、校验并提交 | 对象、validate、提交 | 结束 | 停止并报告 |

## 术语与数据结构

### 范围与前置条件

本节确定入口前置、Bug 定位与写入边界。

- 解析 `REPO_ROOT` 并运行 `doctor`。验收：`normal_workflows_allowed: true`。
- 运行 `git branch --show-current`：为 `master` 或为空（detached HEAD）时在任何写入前停止并报告。
- 参数：
  - 位置参数恰好一个 Bug ID；`--yolo` 可在其前或后。
  - 其他 `--` token 按入口未知参数停止。
  - 缺 ID 或分不清时询问，不猜测，不创建 Bug。
- 定位：运行 `list --repo "$REPO_ROOT" --type bug`（不限 status），
  按完整 ID 命中唯一对象。
  - 也可用去掉 `bug-` 前缀的本体或 `path` 文件名 slug 各匹配一次。
  - 不匹配 title。不逐篇翻阅 `docs/bugs/`。
- 回归检查（仅 `fixed`）：按「红灯」第 1 条重跑该 Bug 所需回归证据记录的命令或 test。
  - 全部通过为仍通过，任一失败为验证失败；缺可执行命令时停止并报告。
- 按对象状态分流：

| 状态 | 去向 |
| --- | --- |
| `closed` 或 `rejected` | 停止 |
| `open` | 进入步骤 2 |
| `fixed` 且回归验证仍通过 | 只读核对对象与回归结果后结束，不写对象、不提交 |
| `fixed` 但验证失败 | 进入步骤 2 续修 |

- ❌ 边界：
  - 不读取当前 Gitflow kind，不 start、不创建或切换 worktree。
  - 写入落点按 `common.md`：master 不直接修改或提交。
  - 不写 child Change，不填 `fixed_in`，不把对象标为 `closed`。

### 澄清

议题固定为「修复 <Bug ID>：根因范围、修复方案、回归证据与排除项」。

- 对照 Bug 的观察到的行为、期望行为、复现步骤、影响与所需回归证据。
- 默认取得用户对共同理解的明确确认。
- `--yolo` 时主 Agent 依据仓库证据与 Bug 正文自裁定共同理解，不向用户提问。
  - 死硬事实不可得仍停止。
- 不得削弱验收或把未确认范围写成已确认。
- ⚠️ `--yolo` 不跳过步骤 3 的红灯。

### 红灯

修复生产实现之前必须先有针对该 Bug 的有效红灯。本步不得改生产实现。

1. 先按所需回归证据运行已有测试：
   - 按 `docs/system/testing/` 的命令模板点名执行对应 test case 或 test。
   - 证据另给可执行命令时运行该命令。
2. 已有测试以该缺陷的断言或期望失败时，记录命令、退出状态与失败断言，
   进入步骤 4，不另造重复用例。
3. 没有失败用例时，先编写能复现该缺陷的回归测试并运行；须得到针对该缺陷的断言失败。
   - 导入错误、编译失败或环境故障不算有效红灯；测试本身有故障时先修好测试再取红灯。
   - 新测试若通过，说明未复现，停止并报告，不改实现。
   - 无法以断言失败复现时停止并报告。

- ⚠️ `--yolo` 不跳过本步，不得在无有效红灯时进入修复。
- 📌 未记录有效红灯不得改生产实现。

### 修复与验证

本节规定修复范围、验证顺序与测试修改权限。

- 只改该 Bug 范围内的实现、必要配置，以及步骤 3 已确认的回归测试。
- 验证顺序：
  1. 先让该红灯测试转绿。
  2. 再按所需回归证据重跑对应命令直到通过；记录命令、退出状态、结果及对应证据项。
  3. 随后对涉及 module 跑 smart（含 quick suite），须退出 0。
     - CLI：`verify --scope smart --repo "$REPO_ROOT"`。
     - 用 `--paths` / `--module` 圈定涉及 module。
     - 不要求交付分支或交付材料；选题按本次修复路径与 Bug 所需回归证据。
     - 成功读 stdout 的 `result`：逐项 `log` 与 quick `report`。
     - 非零读 stderr 最后一行的 `details.results[]`（`passed` / `error`）。
     - 不把进度行当结果，不为查看输出而重跑。
- ❌ 不按分支 kind 选择 smoke 或 release，
  不调用 `$mdf verify --scope branch` 冒充本 intent 完成。
- 不要求 feature 的 design/converge gate。
- 自检发现本阶段可修复的实现问题时原地修复并重验。
  - 可修复指同一失败未满三轮且下一步修复动作明确；否则视为无法完成。
- 测试修改权限：
  - 新增专用于该 Bug 的回归测试属于步骤 3 授权。
  - 修改已有测试的断言、预期、fixture、跳过规则或任何验证门槛，需用户明确批准；
    `--yolo` 不代替该项批准。
- 目标不明、修复未完成、红灯未转绿或验证未通过时停止并报告，不把对象标为 `fixed`。
- 可选加速（见 `common.md`「Jev 可选加速」）：
  - 时机：红灯与回归均通过、准备标记前；tool 可用时。
  - 调用：`noul`（证据是否支持标为 `fixed`）。
  - state：红灯/回归命令与结果摘要。
  - 采信后仍须满足本节验证顺序；未采信或验证未过不得标记。
  - ❌ 不代替用户对改测的批准。

### 标记与提交

本节把 Bug 标为 `fixed`，校验后提交。

1. 将 Bug `status` 改为 `fixed`，不得写 `fixed_in`，不得改为 `closed`。
2. 运行 `validate --repo "$REPO_ROOT" --level basic`，回读对象并核对 `fixed` 与完整 diff。
   - 校验退出 0 且零 finding。
3. 按 `common.md` 提交本次红灯测试、修复、回归验证与对象状态；不夹带无关改动。
   - 提交说明须含完整 Bug ID；release/hotfix 上的直接修复同样适用，供 bug close 定位审查范围。
   - 摘要须区分已验证结论与未验证项，并写明红灯命令与转绿证据。

验收：有效红灯曾失败、现已通过、`fixed` Bug、校验零 finding、提交或明确无新改动。

- 二次验证与关闭对象由 `$mdf bug close <bug-id> --fixed-in <version>` 完成，不在本 intent 把状态改为 `closed`。
