# Heartbeat 状态确认

本契约要求跨 worktree 联调的 Agent 在每轮 heartbeat 时确认双方工作与等待依赖，避免互等。

## 决策树

```text
┌──────────────────────────────────┐
│ 1 Classify event                 │
└────────────────┬─────────────────┘
                 │
                 ├──── 缺少本侧上下文或消息 ID ───────→ [报告缺项并返回失败]
                 ├──── 收到状态询问 ──────────────────→ 2 Reply
                 ├──── 收到状态回复或本轮尚未完成 ────→ 4 Align states
                 └──── 新 heartbeat 轮次 ─────────────→ 3 Ask status

┌──────────────────────────────────┐
│ 2 Reply                          │
└────────────────┬─────────────────┘
                 │
                 ├──── 发送失败 ────→ [保留本轮上下文并报告]
                 └──── 回复成功 ────→ 4 Align states

┌──────────────────────────────────┐
│ 3 Ask status                     │
└────────────────┬─────────────────┘
                 │
                 ├──── 发送失败 ────→ [保留本轮上下文并报告]
                 │
                 ▼ 本轮询问 ID 已记录

┌──────────────────────────────────┐
│ 4 Align states                   │
└────────────────┬─────────────────┘
                 │
                 ├──── 读到业务消息 ──────────────────→ [交回原步，处理后续办 4]
                 ├──── 未获匹配状态回复或仍有歧义 ────→ 4 Align states
                 ├──── 双方互等 ──────────────────────→ 5 Resolve wait
                 └──── 双方已对齐 ────────────────────→ 6 Return

┌──────────────────────────────────┐
│ 5 Resolve wait                   │
└────────────────┬─────────────────┘
                 │
                 ├──── 角色未定或缺外部输入 ────→ [报告依赖并返回原步骤]
                 ├──── 行动未获对端确认 ────────→ 5 Resolve wait
                 │
                 ▼ 行动、负责人和结果已确认

┌──────────────────────────────────┐
│ 6 Return                         │
└────────────────┬─────────────────┘
                 │
                 ├──── 状态证据不完整 ────→ 4 Align states
                 └──── 状态证据完整 ──────→ [返回原步骤，不推进业务关口]

```

## 工作流（唯一执行契约）

在当前 integrate 步骤中处理一个 heartbeat 或状态 send 事件；完成后返回该步骤。
收到状态询问优先回复；收到回复先核对所属轮次，不从文件入口重开 integrate。

| # | 步骤 | 类型 | 做什么 | 证据 | 通过 → | 失败/缺失 → |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | Classify event | 约束 | 核对上下文与事件 | 句柄、ID、当前步骤 | 询问2；回复4；新轮3；续办4 | 缺项返回失败 |
| 2 | Reply | 脚本 | 用 send 回复双方状态，指向询问 ID | 发送成功、reply_to、状态正文 | 4 | 保留上下文并报告失败 |
| 3 | Ask status | 脚本 | 用 send 报告本侧状态并询问对端 | 发送成功、已记录询问 ID | 4 | 保留上下文并报告失败 |
| 4 | Align states | 约束 | 核对本轮状态与依赖 | 双方理解一致 | 互等5；已对齐6 | 业务先返回；其余留4沟通 |
| 5 | Resolve wait | 约束 | 确认行动、负责人和结果 | 行动或外部依赖 | 已确认6；缺条件返回原步骤 | 未确认留5 |
| 6 | Return | 约束 | 保存状态结论，返回当前业务步骤 | 本轮结论与消息关联 | 返回原步骤 | 缺证据回4 |

## 术语与数据结构

### 触发与消息

每轮发出或收到 heartbeat，都由当前 Agent 通过既有 `send` 消息完成状态确认。

- 自动 heartbeat 只证明通道存活，不能证明对端 Agent 正在工作或双方已对齐。
- 本规则适用于通道打开后的各步骤，包括角色未定、计划未就绪、只传与收口等待。
- Agent 至少每 60 秒读取一次后台 Shell 输出；先处理状态询问，再继续当前步骤。
- 状态消息只用于同步，不代替 courtesy 的 ack、角色、计划、验收或收口确认。

### 状态与轮次

Agent 用状态询问与状态回复，对齐本轮双方状态并确认下一步。

- 状态正文以「状态询问」或「状态回复」开头，写明当前工作、等待依赖、下一步与负责人。
  - 明确在等对端的哪个动作或结果，不能只写「等你」；状态回复同时核对对方描述是否一致。
- 运行 `integrate send --repo <本侧> --to <对端> --body <状态正文>`，记录输出的消息 ID。
  - 状态回复追加 `--reply-to <询问ID>`；匹配该 ID 才能作为该轮回复。
- 当前轮次保存在 Agent 的调用上下文中，不新增跨仓状态文件。
  - 已有未完成轮次时，heartbeat 续办步骤 4；不覆盖正在等待的询问 ID，也不并发重开轮次。
- 收到状态询问立即执行步骤 2；回复不产生新询问，双方同时询问也先各自回复。
- 步骤 4 未获匹配回复时，主动沟通并读取本侧 poll；旧回复与自动 heartbeat 均不作为本轮确认。
  - 本侧状态变化时 `send` 告知；有歧义即澄清，不能仅等下一次 heartbeat。
  - 主动询问方须收到关联回复；被询问方核对询问、成功发送回复后核对双方状态，不再等额外 ack。
  - 同时已有本侧未完成询问时，回复对方后仍续办本侧轮次，不覆盖其关联 ID。
- 轮次等待中读到业务消息时，保存完整原文、ID 与原业务步骤，立即交回该步骤处理。
  - 本轮仍未完成，业务消息不当状态回复；处理后续办本轮，不重复 poll 或遗失测试报告、end 等消息。
- 步骤 5 的主导方先指出依赖，再确认谁先做、做什么、产生什么结果。
  - 被动方收到行动后 `send` 确认；主导方实际收到确认才视为行动对齐。
  - 能推进的一侧在原步骤允许的范围内执行并 `send` 告知；角色未定则返回原步骤按其守卫对齐。
- 双方都缺外部输入时，报告具体阻塞与所需输入，保留未完成状态；不冒充已恢复推进。

### 返回与失败

状态确认只解除误解与互等，不改变原步骤的通过条件或跨仓操作范围。

- 有可推进工作就执行；确需等待时，双方明确谁在做什么、本侧等待哪个结果，再继续 poll。
- 角色与计划阶段的状态 `send` 不作为业务确认；收口阶段也不作为测试报告或 `end`。
- 各侧仍只操作本仓、只读取本侧后台 poll，保持原 Goal 与进度，状态确认本身不触发 close-out。
- send 非零、关联 ID 缺失或无法读取后台 Shell 时，返回失败与缺项，由当前步骤走原失败分支。
  - 不停止后台 poll、不丢弃未完成轮次；恢复后从当前轮次续办。
